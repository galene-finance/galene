# Budget engine v1 — implemented integration handoff

This is a backend candidate, not an activated app. The integration owner must wire and test the real authenticated UI; the independent reviewer must review the final source. No live records were read or changed in backend development.

## Entry point and ownership

Import `BudgetEngine` from `$lib/server/budgetEngine/service`. Construct with the existing SQLite connection and **authenticated owner** ID, never a request-supplied owner. It does not open a database, initialize credentials, call a bank, or run timers. Read-only users must not get owner-wide data. Existing demo/session/bearer/write-toggle/CSRF/request-size policies remain mandatory at the route boundary. No new public HTTP handler is installed by this slice.

Use `dashboard(month, obligations, asOfDate)` for the Plan/Home loader: it holds one SQLite read transaction for the view, plan and category states. Use the actual current civil date as the cutoff for the current month; use month end for a completed month. Future-month target planning is permitted, but do not describe future-dated register inflows as received cash. The caller owns trusted clock selection, not the browser request.

## Authoritative DTOs

Public input types are `src/lib/budget/types.ts`. Method result types are inferred/exportable with `ReturnType<BudgetEngine['dashboard']>` etc.; `version` is 1.

- `view`: `revision`, `baseline`, `activityThrough`, `coverageComplete`, `registerStale`, `ledger`.
- `ledger:null` means not activated, before baseline, changed account roster, or stale native register. Never coalesce this to zero.
- `ledger.cashCents` includes signed budget-cash account balances and positive card credits. Negative credit debt and tracking accounts are excluded from assignable cash. Positive card credit is not bank cash; account detail exposes it separately.
- `readyToAssignCents` is unallocated ledger cash. Negative cash category availability and `cashBackingShortfallCents` must remain visible. New assignments are constrained by both RTA and cash overspending; they cannot exploit negative categories to invent spendable money.
- Category `assignedCents` and `activityCents` are selected-month totals; `availableCents` rolls over. Cash overspending persists visibly until covered; this is an intentional transparent policy, not YNAB's automatic month-end transfer to RTA. Credit overspending is separate debt, not negative spendable cash.
- Card `reservedCents` is the allocation ledger amount; `cashBackedReserveCents` is **null** when the overall cash pool cannot back all positive allocations. Never label the raw reserve as payable cash when this is null. `debtCents` and `unfundedCents` remain separate.
- `categoryStates` are the UI's source for financial bubbles. `targetStatus`: no_target / unknown / met / needs_funding. `cashStatus`: unknown / cash_overspent / credit_overspent / unbacked / available / empty. Target met can coexist with empty cash after spending. Unbacked/unknown cash is null, not a green funded number. Keep stable category identity colors independent of these semantic states.
- `plan.totalCents` is current-month target contribution intent, not spending or cash. It is null with no active targets. `lines` retain target/cycle/due/goal/planned/remaining/needed contributions. `fundingKnown` requires complete local activity through the selected cutoff. Funding before activation is not invented; `progressStartsAt` shows the accepted allocation baseline.
- Obligations are already-expanded **outgoing** schedule occurrences supplied by the existing recurrence engine. Do not pass income, raw signed transactions, or aggregate parents plus children. Targeted categories cover their schedules without adding them again. `coveredObligationIds`, `uncoveredObligationIds`, `allProvidedObligationsCovered` and `obligationCoverage` report only provided evidence; they never certify a complete census of household bills.

## Commands

Every mutation takes `{expectedRevision, idempotencyKey}` and returns `{revision}`. Use a fresh key for a new intent, retain the exact payload/key on a retry. Same-key same-payload replay returns the original receipt; changed payload conflicts. Reads after a write verify the result. `BEGIN IMMEDIATE` locks the native-row capture/derived rebuild and assignment. Native SQL INSERT/UPDATE/DELETE on transactions, splits, accounts and categories invalidates the owner's revision, including writes from sync or older handlers.

- `activate({currency,asOfDate,accounts,evidence}, meta)`: explicit one-time end-of-day accepted baseline. Every owner account must be classified `cash`, `credit` or `tracking`, with safe integer balance and the same explicit three-letter currency on every account. Missing balances, omitted accounts and mixed currency are refused. No account/opening/provider balance is overwritten. Initial assignments and reserves are zero; existing card debt is unfunded. **All transactions on or before asOfDate are already in the baseline and excluded.** Do not use a midday snapshot as an end-of-day baseline. Establish a truthful cutoff through the approved owner finance path; otherwise leave activation pending.
- `saveTarget(target,effectiveMonth,meta)` / `archiveTarget(id,effectiveMonth,meta)`: immutable versions preserve older months. Income goals cannot become spending targets. One active target per category, including future effective months. Target IDs cannot change category. Weekly weekday is 0–6 (Sunday–Saturday); the first cycle counts only matching dates on or after startDate (inclusive), while later cycles count the full month. Annual dueDate mandatory; irregular optionally repeats by 1–1200 months. One-time targets stop after their due month. End-of-month dates clamp; recurring anchors retain the original day, so leap-day goals return to February 29 in leap years. Dates are civil ISO dates, independent of DST.
- `allocate(event,meta)`: assign signed cents from/to RTA, move positive cents between categories, reserve signed cents for a credit account. These are budget records, not bank transactions/payments. Removing an allocation is an explicit inverse assignment/move/reserve, not deleting history. All selected account/category references are owner-checked. Backdated commands revalidate affected later allocations through the full known activity/commitment horizon and cannot worsen cash backing at any affected day-end. Rejection rolls back the staged event, revision and receipt together; a later corrective command can still repair a deficit revealed by a legitimate source correction. Projection is civil-day based: allocations precede posted activity on the same date, and postings use deterministic native transaction-ID order. This is a daily budgeting convention, not a claim of intraday bank event timestamps.
- `refreshRegister(through,pairs,meta)`: preferred production bridge. Captures all native owner posted rows after the baseline, validates splits, excludes pending, and replaces only derived posted events atomically. Existing native transaction rows are never edited. Pair entries `{outflowId,inflowId,categoryId?}` require explicit identity, equal/opposite amounts, distinct accounts, transfer classifications, no splits and the same civil date. Do not guess pairs from amount/date. Unpaired or split/multiday transfers, uncategorized rows, invalid splits or unknown baseline accounts block completion for review. Income reversals reduce income/RTA; refunds return to the spending category; internal transfers/payments never add expenses. Credit-to-credit reserve transfer and budget/tracking crossings are supported after explicit normalization. An outgoing budget-to-tracking transfer needs an allocation category.
- `replacePosted(events,coverage,meta)`: trusted internal normalized seam, not a bank importer or public client write API. Requires complete baseline-next-day through-current coverage and `tx:` source IDs. Never use partial provider pages. Native edits/deletes refresh the same identities; do not append corrections as duplicate transactions. Integration should prefer `refreshRegister` and use this method only with equally authoritative fully validated data.
- `recordSnapshot(sourceKey,snapshot,meta)`: append-only timestamped evidence; same source key with conflicting payload is refused. Required currency, account, safe integer amount, exact UTC timestamps and nonempty evidence. Source is actual / accepted_estimate / reconstructed. Preserve the accepted estimate method and source-specific account mapping; do not overwrite it with another feed. Call only during an authorized durable sync/update, not from a read-only page load.
- `history(accounts,dates)`: explicitly included owner accounts/debts and optional inclusion dates. No silent carry-forward. Every missing expected account makes total null, preserving known subtotal and missing IDs. Actual and accepted estimates stay distinguishable. Mixed currency is refused, never converted implicitly.
- Pure `reconstructHistory` requires a day-end anchor plus complete bounded posted transaction evidence. Partial history returns no generated points. Reconstructed points record anchor source and exact coverage. Do not call it on provider samples, unverified opening balances or merely exhausted truncated pages.

## Existing limits and migration

One additive native migration creates engine tables and invalidation triggers. Existing budgets are copied, unchanged, into `budget_engine_legacy_targets` with cadence/amount/category and review status, **not** allocation events or balances. `legacyTargets()` exposes these target drafts; they must be shown/adopted in the target editor rather than silently disappearing. Due dates, weekly anchors and refill/set-aside choices absent from the old limit model cannot be recovered by arithmetic. Use `saveTarget` with accepted settings. Competing legacy cadences for one category require selection, not summing. Native budget rows, scheduled series, imports, account IDs, balances and all transaction histories remain untouched.

The migration SQL supports transactional dry-run rollback on a synthetic database. Deployment rollback should restore the reviewed app image while retaining additive data, or use the approved database recovery procedure that preserves later writes. Do not drop new engine tables or restore an old database over newer owner transactions merely to revert a UI build.

## Acceptance and remaining integration/data gates

Implemented: target evaluator, ledger/reallocation/reserves, versioned persistence, native normalization/rebuild, revision/idempotency/concurrent-writer protection, history/reconstruction and authoritative bubble DTOs. Test with synthetic fixtures only until integrated review.

Still required from the integration/QA owners: authenticated route guards and UI forms, legacy-target adoption UX, explicit accepted end-of-day baseline and account scopes, classification/pair review for actual incomplete data, source-specific snapshot capture in the approved update path, and app-backed bubble/reload/phone/keyboard acceptance. Adding/removing accounts after activation deliberately invalidates coverage; do not silently replace the baseline or label those accounts zero. An explicit baseline/account-scope transition UI is outside this first engine slice and must preserve prior allocation history if added.

No historical balances have been invented; no claim is made about how much usable real backfill exists. Unsupported/unresolved data is a visible gap, not a fake successful migration. W11 alone integrates/deploys privately; W17 owns the independent source and integrated behavior verdict.
